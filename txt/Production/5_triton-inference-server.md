Представим, что мы обучили модель и теперь хотим её использовать. 
Например это детектор объектов, (например людей) и дальше будем делать поиск объектов представляющих интерес по их эмбеддингу (например, потенциальных покупателей).

Для этого на сервере нужно запускать несколько моделей: 
YOLO для поиска ограничивающих рамок (bounding boxes)
 Эмбеддер
Одну или несколько моделей для анализа содержимого этих рамок

Возникает задача эффективного распределения GPU-ресурсов между моделями.

#slide
Существует две конфликтующие метрики:

**Пропускная способность (throughput)** - Показывает сколько запросов в единицу времени обрабатывает система. Чем выше throughput тем эффективнее используется GPU. Самый простой способ увеличить пропускную способность это использовать большой батч. Однако это приводит к задержкам: кадры накапливаются в очереди, что недопустимо для систем реального времени. Например, при работе с детектором движения полный батч может не накопиться за время перемещения объекта перед камерой. 
Соответственно нужно одновременно принимать во внимание **Задержку (latency)**:
это среднее время ответа системы на запрос пользователя.  Приоритет низкой задержки означает что ресурсы будут недоиспользоваться.
На практике обычно отталкиваются от максимально допустимой задержки и подстраивают под нее конфигурацию для загрузки GPU.

#slide Варианты развертывания

Как вообще можно развернуть модель на сервере

*Наивный* (не рекомендуется): запуск Python-скрипта на  веб-сервере. 
PyTorch не оптимизирован для инференса,  
Конвертация в ONNX ускоряет работу, но это всё равно не оптимальный пайплайн.
Загрузка модели при каждом запросе неэффективна, поэтому можно использовать сервер приложений.
*Промежуточный*: использование gRPC-сервера.
Неплохо оптимизирован, 
использует быстрый бинарный формат и генерирует клиентский код автоматически по описанию в proto-файле.
Но! Логику обработки батчей и управления инстансами нужно писать вручную.
*Продакшн-уровень*: использование Triton Inference Server от NVIDIA. Эта платформа эффективно управляет ресурсами GPU на одном физическом сервере (и может масштабироваться на кластере), избавляя разработчика от головной боли по созданию экземпляров моделей и формированию батчей.

#slide
Triton Inference Server
Ключевые возможности:
Назначение оптимизация использования GPU on Nvidia для **инференса** моделей
Работает с моделями в форматах TorchScript и ONNX (сырые модели PyTorch не поддерживаются).
Гибкая настройка батчинга: можно задать желаемые размеры батчей (обычно степени двойки) и таймаут ожидания для их заполнения.


#concurrent_execution
Автоматическое управление несколькими инстансами одной модели в памяти. Веса общие т.е. загружаются один раз и не расходуют память.
Несколько инстансов позволяют обрабатывать запросы параллельно без ожидания освобождения модели.

Процесс запуска
#model_convertation
Заявленная поддержка Pytorch относится только к torchscript. Рекомендованный и наиболее универсальный формат для конвертации — ONNX.
Конвертация модели в ONNX:
Указываем имена входных и выходных тензоров
Фиксируем размер входных данных
Задаем размерности входа, которые могут изменяться от запуска к запуску (размер батча).
При успешной конвертации модель сохранится в виде одного или двух файлов на диск.

#per-model-config
Модели размещаются в определённой структуре папок на диске.
Рядом с ней создается конфигурационный файл. В нём указываются:
Название модели и платформы.
Имена и типы входных/выходных тензоров.
Размерность входных данных (без учета размерности батча).
Количество инстансов (веса будут общими)
Настройки батчинга (batching): желаемые размеры батчей и таймаут. После истечения таймаута в модель будет отправлен батч максимального размера.

Instances vs Batches

#monitoring
Мониторинг
Triton возвращает метрики в формате, который позволяет собирать их при помощи Prometheus и затем визуализировать в Grafana. Что позволяет оценивать загрузку и оптимизировать конфигурацию используя эту стандартную связку.

Особенности

При ошибке (например Out of Memory) Triton выгружает модель из памяти и не пытается пересоздать ее.
Но ошибка в  одной модели, не влияет на остальные.

Сам по себе Triton не масштабируется на несколько машин. Но так как это контейнерное решение, то на кластере можно запускаеть несколько контейнеров с Triton использeю балансировщик нагрузки.

Таким образом, Triton позволяет эффективно балансировать задержку и пропускную способность, автоматизируя управление ресурсами GPU в продакшн-среде.
